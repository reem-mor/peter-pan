# INC-2423 — bad deploy rolled back after error-rate spike (2026-06-27)

**Severity:** P2 · **Duration:** 19 min · **Class:** change_related

**What happened:** the 14:05 deploy of the orders API shipped a serialization
change that dropped a required field from the event schema. Consumers began
rejecting messages and the orders API error rate climbed from 0.2% to 11% within
three minutes. The change had passed CI because the contract test asserted the
new shape, not backward compatibility with in-flight consumers.

**Detection:** error-rate alert (T+2m) correlated by the change-timeline against
the deploy marker. **Resolution:** one-click rollback to the previous revision
after on-call approval (T+16m); error rate returned to baseline in two minutes.
No data was lost — rejected events were replayed from the dead-letter queue.

**Lessons:**
- Schema changes now require a backward-compatibility contract test, not just a
  current-shape assertion.
- Rollback stayed fast *because* it was a pre-approved, reversible action behind
  the ActionPreview gate — the approval step was seconds, not the bottleneck.
- Reference the canary-rollback runbook; expand-then-contract is the safe order.
